# 更新日志规范

三个载体，三种读者。同一件事只写一次，写多深由读者决定。

## 分工

| 载体 | 位置 | 读者 | 该说什么 | 上限 |
| --- | --- | --- | --- | --- |
| 应用内日志 | `src/shared/releases.ts` | 已安装的用户，在「关于 → 更新日志」里翻 | 升级后会看到什么不同 | 每条 40 字，每版 5 条 |
| README 版本历史 | `README.md` 表格 | 第一次见到这个项目的人 | 这个软件在往哪个方向迭代 | 每行 60 字 |
| GitHub Release | `.tmp/release-notes-X.Y.Z.md` | 想复现问题、排查故障的人 | 根因、复现步骤、验证方式、已知限制 | 不限 |

技术细节只允许出现在第三处。前两处出现错误码、日志原文、文件路径，就是写错了位置。

## 写作规则

### 一条只讲一件事

三个修复写三条，不要压成一段；同一件事的起因与结果不要拆开。

### 一律第三人称

对外文字不出现第二人称，不分载体、不分语种。读者是谁不改变写法。

- 中文不用「你」「您」；英文不用 you / your；西语不用 tú / te / tu；日文不用「あなた」。
- 立场是项目维护者本人，不是旁观的第三方：不写「帮你」「由 AI 生成」「本文档自动生成」这类旁观视角。
- 需要指代使用者时写「用户」，或者直接省略主语（`点选后设置窗口立刻变色`）。
- 不劝诱、不寒暄、不惊叹：`只需`、`快试试`、`轻松`、`一键搞定` 一律不写。
- 不是命令式的操作指引不要写成「请……」；界面内的按钮说明按 UI 文案处理，可保留礼貌祈使。
- 测试与校验脚本输出的提示同样适用：过程细节可以写，语气按上面的标准，不写成对话。

- 好：`安装失败也会自动重开，不会只剩一个空桌面`
- 差：`装不上也别担心，它会自动帮你重开的`

「迷你窗口」这类音译词里的「你」不是人称，校验时会先剔除再判断。

### 用结果陈述，不用「修复了 X」

`kind` 字段已经标明是修复，正文不必再说一遍。

- 好：`安装失败也会自动重开，不会只剩一个空桌面`
- 差：`修复了安装失败后不重启的问题`

### 写用户看得见的，不写怎么做的

留下来：可见现象、界面位置、快捷键、用户能对照的数字（秒数、内存占用、条数）。
移出去：错误码、事件 ID、文件与目录名、函数与变量名、样式 token 名、提交号、断言数、日志原文、命令行参数。

判断标准：这句话描述的变化，用户是否能在界面上找到？找不到就删。

### 长度

- 应用内：中文 40 字/条，英文 110 字符/条，日文 90 字/条，西语 130 字符/条
- README：中文 60 字/行
- 超了先砍定语，不要砍信息；一句话讲不完的，多半该拆成两条

### 四语齐平

`zh` / `en` / `ja` / `es` 必须都有，分句数一致，不增不减。日语用「です・ます」体，西语用陈述式。

### 排序

按用户遇到的概率排，不按提交顺序。最容易撞上的放第一条。

### 什么不进应用内日志

- 纯内部改动：CI、重构、测试、依赖升级、日志与注释
- 只有开发者能感知的指标：断言数、覆盖率、代码行数
- 只有极端个例才会碰到的边界情况

这些只进 GitHub Release。

## 校验

```bash
npm run test:releases
```

检查 1.2.19 及以后的条目：中文长度、四语齐全、每版条数上限、禁用模式（错误码、盘符路径、文件名、命令行参数、样式 token），以及全部版本的称呼与语气（第二人称、劝诱词）。CI 里有一步跑它。

结构规则只覆盖 1.2.19 及以后，因为更早的条目按旧习惯写成，改动会牵动已发布的记录；称呼规则对全部版本生效，不分新旧。
